# human_passport_score

Proves, without revealing the wallet, the attestation or the exact score:

> The wallet that signed this request holds a Human Passport **scoreV2**
> attestation, signed by an issuer key the verifier accepts, scored at least
> `min_score` by scorer `scorer_id`, and not expired at `now`.

| | |
|---|---|
| Canonical id (`Nargo.toml` name) | `human_passport_score` |
| Directory | `human-passport-score/` (library: `human-passport-libs/`) |
| Solidity verifier | `target/HumanPassportScore.sol` (generated by `scripts/build.sh`) |
| Public inputs | 195 fields (6 x 32 bytes + 3 scalars), order below |
| Size | see "Measurements" |

## What Human Passport publishes, and what of it a circuit can check

Human Passport (human.tech, formerly Gitcoin Passport) publishes scores in two
places. Only one of them is signed.

1. **The Passport API** (`GET /v2/stamps/{scorer_id}/score/{address}`) returns
   score, threshold, stamps and expiry as plain JSON. No signature, no
   attestation. A circuit cannot check it.
   (docs.passport.human.tech/building-with-passport/stamps/passport-api/api-reference)
2. **Passport onchain**: the Passport app asks Passport's server for a signed
   request, and the user submits it to `GitcoinVerifier.verifyAndAttest()`,
   which checks an EIP-712 signature by the `issuer` key and writes an EAS
   attestation through `GitcoinAttester`. The resolver caches the score.
   (github.com/passportxyz/eas-proxy, `contracts/GitcoinVerifier.sol`,
   `GitcoinResolver.sol`, `deployments/onchainInfo.json`, read at
   `1311b99`, 2026-10-28)

The issuer's EIP-712 signature is the cryptographic object. Rebuilding its
digest from a real Base transaction (`0x9ca4f8e9...a38d`) recovers
`0x804233b96cbd6d81efeb6517347177ef7bD488ED`, equal to `issuer()` on the
verifier. The same key is `issuer()` on Base, OP, Arbitrum, Linea, Scroll,
zkSync Era and Shape (`eth_call 0x1d143848` on each chain's verifier from
onchainInfo.json, 2026-10-28). The testnets (OP Sepolia, Ethereum Sepolia,
zkSync Sepolia) list a different issuer, `0x5f603Ed9...B167`, in the same file.

Measured on Base through `base.easscan.org/graphql`, 2026-10-28: 17,746
scoreV2 attestations since 2025-03-13, **0 revoked**, 307 issued in the last
90 days and all 307 unexpired. Every recent one: one request, one entry,
scorer 335, 4 decimals, threshold 200000, expiry 90 days after issue.

### What the signed request contains

`PassportAttestationRequest { MultiAttestationRequest[] { schema,
AttestationRequestData[] { recipient, expirationTime, revocable, refUID, data,
value } }, nonce, fee }`, hashed with EIP-712 under domain
`GitcoinVerifier / "1" / chainId / verifier address`. So the signature binds
the chain, the verifier contract, the schema, the recipient, the expiry and
`keccak256(data)`; `data` carries the score in its head and every stamp after
it. It does **not** contain an issue time, and nothing in it changes when the
attestation is revoked.

## The statement, checked in this order

`human-passport-libs/src/issuer.nr::verify_score_statement`, then the wallet
and nullifier in `src/main.nr`:

1. **Score data head** (`score_data.nr`): `data_len` in `[192, MAX_DATA_BYTES]`;
   the five static words read exactly as Solidity's `abi.decode` reads them
   (unused high bytes must be zero), `score_decimals == 4`, stamps offset
   `0xc0`. Any other decimals is refused rather than rescaled, because it
   would change what `min_score` means.
2. **Issuer signature**: the EIP-712 digest of a request with exactly one
   MultiAttestationRequest holding exactly one entry, `recipient =
   user_address`, verified (secp256k1) against the prover-supplied issuer key.
   The one-element array hashes are fixed, so an entry cannot be picked out of
   a larger signed batch.
3. **Issuer list**: `keccak256(issuer ++ passport_domain_separator ++
   schema_uid)` is a leaf under the public `signer_list_merkle_root`. All three
   are in the leaf: the key is what signs; the domain names the chain and
   verifier contract (the same key signs on every chain); the schema uid
   differs per chain and fixes which data layout step 1 applied.
4. **Expiry**: `now < expirationTime` (which also refuses EAS's "never expires" 0).
5. **Score**: `scorer_id` equals the public input, `score >= min_score`.
6. **Wallet**: the wallet's key signed either an EIP-712 action
   (`domain_separator`, `action_hash`) or, with no action, `signal_hash`
   under personal_sign. Exactly one mode; shared `signed_digest`.
7. **Nullifier**: `keccak256(keccak256(user_address ++ keccak256("human_passport_score")) ++ scope)`,
   the shared `verify_wallet_nullifier` (as giwa_attestation and the Coinbase
   v2 work). No prover-chosen input enters it.

### Public inputs (ABI order)

| # | Name | Fields | Meaning |
|---|---|---|---|
| 1 | `signal_hash` | 32 | personal_sign challenge; zero in action mode |
| 2 | `domain_separator` | 32 | EIP-712 domain of the action; zero without one |
| 3 | `action_hash` | 32 | EIP-712 hashStruct of the action; zero without one |
| 4 | `signer_list_merkle_root` | 32 | root over (issuer, Passport verifier domain, scoreV2 schema) leaves |
| 5 | `scope` | 32 | Sybil domain |
| 6 | `nullifier` | 32 | see 7 above |
| 7 | `min_score` | 1 | threshold x 10^4 (20.0 = `200000`) |
| 8 | `scorer_id` | 1 | Passport scorer the score belongs to (Base onchain: 335) |
| 9 | `now` | 1 | unix seconds |

Offsets: 0, 32, 64, 96, 128, 160, 192, 193, 194 -- the first six are
giwa_attestation's layout, unchanged.

**Issuer list construction.** Leaves in list order, padded with `bytes32(0)` to
a power of two, parent = `keccak256(left ++ right)`, depth at most 8. The root
the verifier publishes for Base is over the issuer on both Base verifiers
(the fixtures add a third, test, leaf).

### What the verifier (our core/SDK, or a contract) must still check

- `signer_list_merkle_root` equals the root it publishes, `scorer_id` is the
  scorer it means, `min_score` is the threshold it asked for, `scope` and the
  action/signal are its own.
- **`now` is close to its own clock.** The circuit only checks
  `now < expirationTime`; a proof with `now = 0` would pass any unexpired-ever
  attestation. Same rule as OIDC v2's `now`.

## What this does NOT prove

- **Revocation.** The signed request does not change when the attestation is
  revoked, so a revoked attestation still proves until it expires. Only the
  attester's owner (a 1-of-2 Safe on Base) or an allowed verifier can revoke;
  none of 17,746 has been revoked. Checking it would need the EAS record or the
  resolver's cached score by storage proof against a trusted state root
  (measured on Coinbase KYC: about 97k gates per MPT level, about 1.2M at 10
  levels; `coinbase_eas_storage_poc`), or an App Attest / server signature over
  a lookup, as Coinbase KYC v2 does.
- **That this is the wallet's latest score.** Each new issuance replaces the
  resolver's cached score, but an older signed request with a higher score
  stays valid here until its own expiry (at most 90 days).
- **That the request was submitted on chain.** The issuer's signature is the
  statement; a signed request that was never sent proves the same thing.

## Data cap

The issuer signs `keccak256(data)`, and `data` grows with the stamps (about
192 bytes per stamp), so the in-circuit keccak over `data` is most of the
circuit and its cap decides who can prove at all.

Base, all 17,746 scoreV2 attestations: min 224, median 1,824, p95 3,168, p99
4,096, **max 5,888 bytes** (35 stamps, attestation `0x0803d33e...1249`).
Nothing on chain caps the number of stamps.

Measured with `bb gates` (whole circuit, only the cap changed):

| `MAX_DATA_BYTES` | gates | dyadic size |
|---|---|---|
| 6,144 | 1,404,723 | 2^21 |
| 8,192 | 1,710,123 | 2^21 |
| **10,240 (chosen)** | **2,015,523** | 2^21 (81,629 = 3.9% headroom) |

About 149 gates per data byte (about 20k per 136-byte keccak block); the rest
is about 0.49M. At 2^20 the cap would be about 3.7 KB, which is below Base's
p99, so 2^20 is not an option without leaving out real users. Within 2^21 the
proving cost is set by the dyadic size, so the cap is taken as large as fits:
10,240 bytes, about 1.7x the largest passport on Base (about 52 stamps).
A passport larger than that cannot be proved and is refused with
"score data longer than the circuit allows".

## Fixtures and acceptance

```
scripts/build.sh human-passport-score        # compile, vk, verifier, SRS, then:
scripts/human-passport/acceptance.sh          # (run by the post-build hook)
scripts/human-passport/make-fixtures.sh [tx]  # regenerate (needs a Base RPC)
```

There are two kinds of fixture, both from real Base issuances
(`scripts/human-passport/generate-fixtures.js`):

- **`../human-passport-real-issuer-check/`** -- a small program running the same
  `verify_score_statement` on three REAL `verifyAndAttest` transactions: the
  real issuer signature, the real data (1,184 bytes via `0x45fA`; 544 bytes,
  2 stamps; and the largest on Base, 5,888 bytes via `0x16db`). Before writing
  them the generator recovers the issuer and compares it with `issuer()` on
  chain. Executed, not proved; not a shipped circuit.
- **The full circuit** -- the first issuance's real `data`, re-signed by an
  INSECURE TEST ISSUER for an INSECURE TEST WALLET (keys derived from public
  strings in the generator), under an issuer list that holds the real issuer
  on both Base verifiers plus the test issuer. Every refusal case changes one
  thing relative to the accepted fixture and must be refused with its named
  message; refused for another reason counts as a failure.

`Prover.toml` and every `test-vectors/` are gitignored like the rest of this
repo. Fixture names are dot-free on purpose: nargo 1.0.0-beta.19 treats
anything after a dot in `--prover-name` as an extension and replaces it with
`.toml`, so `--prover-name Prover.no-action` silently reads `Prover.toml`
(checked: `--prover-name Prover.does-not-exist` succeeds). The acceptance
script refuses a dotted name or a missing fixture file.

Mutation check (`scripts/human-passport/mutation-check.sh`): deletes one guard
at a time and requires the case written for it to be accepted. Its first run
found a separate `expirationTime != 0` guard unreachable (`now < 0` already
fails), so it was removed.
